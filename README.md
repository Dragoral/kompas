# Клинический компас

Веб-прототип поддержки принятия врачебных решений при тревожно-депрессивной симптоматике. Система не выполняет клинические действия автономно; назначения, изменения плана и маршрутизацию подтверждает врач. До клинической, правовой и ИБ-проверки не использовать для реального лечения.

## Запуск

Требуются Docker Compose, Python 3.11+ для локальных проверок и Node.js 20+ для frontend.

1. Скопируйте `.env.example` в `.env`.
2. Задайте уникальные `POSTGRES_PASSWORD`, `MASTER_KEYS`, `DEMO_PASSWORD` и точный `CORS_ORIGINS`. Для `MASTER_KEYS` сгенерируйте 32 случайных байта и закодируйте их в Base64; например, запустите `python -c "import secrets,base64; print('k1:'+base64.b64encode(secrets.token_bytes(32)).decode())"` и вставьте результат целиком. Храните ключ отдельно от резервных копий и не используйте ключ из примера.
3. Запустите `docker compose up --build -d`.
4. Интерфейс доступен на `http://localhost:8081` (или указанном `WEB_PORT`). API по умолчанию доступен только внутри docker-сети через web/nginx.

Файл `.env.example` настроен для **локальной демонстрации на синтетических данных** (`APP_ENV=development`). Это не конфигурация для реального лечения. При `APP_ENV=production` приложение дополнительно отказывается запускаться, если активные шкалы, правила маршрутизации/алертинга, лекарственные справочники или источники не имеют `verified: true`. Этот флаг можно выставлять только после проверки уполномоченным клиническим специалистом по актуальному официальному источнику и документирования рецензии; сама программная проверка не заменяет такую рецензию.

Для production обязательно обеспечьте HTTPS на обратном прокси и ограничьте доступ к хосту/БД. Значение `NOTIFY_PROVIDER=log` — только тестовый режим, не настоящая доставка экстренных SMS.


## Интерфейс приложения

Интерфейс построен на React, TypeScript и Vite. Для всех авторизованных ролей используется общий адаптивный каркас: боковая навигация по ролям, верхняя панель, быстрые действия, хлебные крошки, мобильное меню и зона живых событий. Роли имеют раздельные разделы:

- **Врач:** список пациентов с четырьмя фильтрами, клинические оповещения, очередь клинических решений, карточка пациента, терапия, шкалы, визиты, документы/извлечение данных, сообщения, FHIR-экспорт и база знаний. Клиническая аналитика и согласование доступны только врачу-рецензенту.
- **Пациент:** обзор, согласие, дневник, шкалы самоотчёта, история, сообщения, нежелательные реакции, доверенные контакты, экспорт собственных данных и зашифрованная офлайн-очередь разрешённых записей.
- **Администратор:** состояние системы, технические метрики, клиническая аналитика, пользователи, пациенты/смена лечащего врача с подтверждением, аудит и справочники с версиями/перезагрузкой YAML.

Врачу доступен поиск по пациентам из верхней панели. На странице пациентов отображается сводка по текущему списку и таблица с показателями; это агрегаты для навигации, а не самостоятельные клинические решения. Для экстренных сценариев интерфейс показывает живые события, однако браузерные уведомления не заменяют реально настроенный канал экстренной связи.

Для локального запуска фронтенда отдельно: `cd frontend`, `npm ci`, `npm run dev`. Для проверки перед сборкой: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`.

## Первый администратор

После запуска API создайте учётную запись без сброса существующей базы:

```bash
docker compose exec api python -m app.cli create-admin --login admin01 --name "Администратор системы"
```

Пароль запрашивается скрытым интерактивным вводом и не передаётся в аргументах команды. Подключите MFA после первого входа. CLI не создаёт демо-пользователей.

## Проверки

Проверить, что все API-пути отражены в матрице интеграции frontend/backend:

```bash
python tools/check_route_coverage.py
```


```bash
cd backend && python -m pytest
cd ../frontend && npm ci && npm run typecheck && npm run lint && npm test && npm run build
```

Тесты требуют зависимостей из `backend/requirements.txt` и доступных сервисов, предусмотренных конкретным тестом.

## Что остаётся обязательным

- Медицинский специалист должен сверить русские валидированные тексты шкал, критерии маршрутизации, лекарственные инструкции и клинические рекомендации по актуальным официальным источникам. Программные проверки такую верификацию не заменяют.
- Для живых критических уведомлений необходим реально настроенный и проверенный SMS/телефонный канал и резервная эскалация. Одного отображения события в браузере недостаточно для эксплуатации.
- Зашифрованные резервные копии PostgreSQL и периодический restore drill реализованы через `app.backup_postgres`; проверьте доступность `pg_dump`/`pg_restore`, права `CREATEDB`, политику хранения и результаты `data/backup_drill.json` на стенде.
- Добавлены PWA manifest/service worker и зашифрованная офлайн-очередь разрешённых пациентских записей с синхронизацией `/api/me/sync`. Интеграционные испытания установки PWA, сетевых переходов и восстановления очереди в браузере ещё не завершены; не считать эту возможность полностью готовой к эксплуатации без таких испытаний.
- Перед апробацией с реальными пациентами нужны юридическая проверка, анализ угроз и рисков, клиническая апробация и процедура реагирования на инциденты.


## Изменения оболочки интерфейса (19.10.2026)

- Перед вводом учётных данных пользователь обязан выбрать роль: врач, пациент или администратор. Роль подтверждается сервером; выбранный пункт не заменяет серверную проверку полномочий.
- В кабинете врача четыре карточки сводки работают как переключатели фильтра списка: все пациенты, активное наблюдение, требующие внимания и обязательная маршрутизация. Карточка «Требуют внимания» получает яркую красную подсветку, когда в текущем наборе есть хотя бы один пациент с критическим/высоким сигналом, обязательной маршрутизацией или ожидающим клиническим действием.
- Внизу навигации указано `@by негрусteam` полупрозрачным шрифтом и подпись «Демо-версия».
- Нижняя юридическая заметка выделена красным блоком; по краям экрана анимированная синяя, розовая и зелёная градиентная линия. Карточки получили более выраженные тени.
- Создан автономный интерактивный предпросмотр `kompas-interface-preview.html`. Он использует синтетические данные и не подключается к API.

Проверка frontend-сборки на этой машине не завершена: `npm ci --offline` остановился из-за отсутствующего пакета в npm-кэше, сетевой `npm ci` не завершился в доступное время. Синтаксический разбор 72 файлов TypeScript/TSX прошёл без ошибок, но полноценный `tsc` не удалось запустить из-за отсутствующих npm-зависимостей и типов `node`/`vite/client`.


### Исправление предпросмотра входа

Экран входа и рабочий кабинет переключаются взаимоисключающе. Неактивная `.screen` скрывается через `display: none !important`, чтобы её нельзя было показать повторно стилями вложенной сетки. Выйдите через «Выйти из системы», чтобы вернуться к экрану авторизации.

## Полнота интеграции API

- Матрица `docs/frontend-backend-coverage.md` связывает **93 зарегистрированные комбинации HTTP-метода и API-пути** с frontend-страницей, компонентом или внутренним транспортным обработчиком. Дублирующий alias визита обслуживается действующим экраном истории визитов/быстрого очного приёма; служебные health/SSE-ticket операции выполняются внутри интерфейса.
- Последние технические проверки зафиксированы в `docs/integration-test-report.md`. Полный frontend build/typecheck не подтверждён: `npm ci --offline` вернул `ENOTCACHED`, а сетевой запуск установки завершился по тайм-ауту; это нельзя считать доказательством безошибочной production-сборки.
